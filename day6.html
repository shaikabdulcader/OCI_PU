05Vault & Secrets

Secrets Management — Don't Write Passwords in Code

Database passwords, API keys, SSH keys, tokens — these are SECRETS. Where you keep them decides whether a leaked repository becomes a disaster. Choose an approach, then let a hacker read your GitHub.

🕰
Secret VersionsVault keeps versions of each secret — rotate the DB password and apps fetch the new version automatically, while the old one is kept for rollback. No redeploys, no passwords in code, full audit trail.

🎯 Scenario Drill — which one?

1. Encrypt a 2 TB database volume.
✓ Symmetric (AES) — huge data needs speed; one key locks and unlocks the whole volume.
2. Log into your OCI VM without a password (SSH).
✓ Asymmetric (RSA) — public key on the VM, private key on your laptop. Authentication = asymmetric's job.
3. Two strangers (your browser & a bank server) must agree on a secret over the open Internet.
✓ Asymmetric — secure key exchange. (Fun fact: TLS then switches to a fast symmetric key for the actual data. Both, in sequence!)

11Data Protection

PKI, Certificates & Certificate Authorities

One question TLS must answer first: "Is this REALLY my bank's server — or an impostor?" Certificates are ID cards for servers, and Certificate Authorities (CAs) are the passport offices that issue them.

Your browser connects to a website. Check its certificate:

🕵️ You be the browser — trust or block?

Three sites present their ID cards. Your trusted passport-office list: DigiCert, Let's Encrypt, GlobalSign. Judge each:

1. yourbank.com — certificate signed by DigiCert, valid until 2027.
✓ Trust. DigiCert is on your trusted CA list — a real passport office vouched for this site.
2. y0urbank.com (note the zero!) — certificate signed by… itself.
✓ Block. A self-signed certificate is an ID card the impostor printed at home. No trusted CA = full-page warning. (Also: look at that domain name…)
3. myblog.com — a small hobby blog, certificate signed by Let's Encrypt (a free CA).
✓ Trust. Free ≠ fake: Let's Encrypt is a genuine trusted CA. What matters is WHO signed, not how much it cost.

13Key Lifecycle

Who Manages the Keys?

Oracle-managed = Oracle creates and guards the keys (easy). Customer-managed = YOU create and control them in Vault (control + compliance). Pick the right one per company.

Oracle-Managed Keys
EASY MODE
Oracle creates, stores, rotates. Zero effort — encryption just works. Great default for most apps.
vs
Customer-Managed Keys
CONTROL MODE
You create keys in YOUR Vault, control rotation & access, can revoke instantly. Required in finance, healthcare, government.

🧾 Who does what? Flip the mode and watch the jobs move

🎯 Scenario Drill — pick the mode

1. A student project hosting a recipe blog.
✓ Oracle-managed — encryption by default, zero key admin. Perfect when compliance doesn't demand control.
2. A hospital storing patient records (HIPAA compliance).
✓ Customer-managed — compliance requires the hospital to control key lifecycle, access and revocation.
3. A central bank that must prove keys NEVER leave certified tamper-proof hardware.
✓ Customer-managed with HSM protection — keys live inside a FIPS-certified Hardware Security Module and never leave it.

16Wrap-Up

Cheat Sheets

Encryption Basics

  • Encryption = readable → unreadable without the key
  • Symmetric = same key (AES, fast, big data)
  • Asymmetric = public + private pair (RSA, SSH, TLS)

Vault & Keys

  • Vault stores keys, secrets, certificates — never with the data
  • HSM mode = keys never leave certified hardware
  • Oracle-managed = easy · Customer-managed = control/compliance
  • Rotate keys; replicate for DR; secrets have versions

Data Protection

  • At rest = encrypted on disk (default in OCI)
  • In transit = TLS/HTTPS tunnel over the network
  • Certificates = server ID cards, issued by trusted CAs (PKI)

Best Practices

  • Never hardcode passwords — fetch from Vault
  • Least-privilege IAM on keys & secrets
  • Bastion for admin access · NSGs/Security Lists on VMs
  • Audit everything — every key use is logged
