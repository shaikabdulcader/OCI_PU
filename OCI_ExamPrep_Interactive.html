Cloud Foundations & IAM

OCI's physical layout (regions → ADs → fault domains), who owns what in the cloud, how you carve a tenancy into compartments, and how identity plugs it all together.

1.1Resiliency Architecture

Regions, Availability Domains & Fault Domains

Three levels of physical isolation. Each protects against a different kind of failure — and the exam will ask you which is which.

Largest

🌍 Region

A geographic area (e.g. Mumbai, Frankfurt) containing one or more ADs. Protects against city-level or country-level disaster.

Mid

🏢 Availability Domain (AD)

A physically separate data center within a region. Its own power, cooling, and network. Protects against DC-wide failure.

Smallest

🖥️ Fault Domain (FD)

A logical grouping of hardware inside one AD. Three FDs per AD. Protects against rack-level or hardware failure.

1.2Cloud Foundations

Shared Responsibility Model

The cloud doesn't do everything for you. Oracle secures the infrastructure; you secure what you build on top.

The line between "Oracle's job" and "your job" moves depending on the service model. In IaaS, you own more (guest OS, patches, apps). In PaaS, Oracle handles more (OS, runtime). In SaaS, you basically own only your data and users.

OracleIaaSYou

What each side ALWAYS owns

Oracle always securesYou always secure
Physical facilities, hardware, hypervisor, network fabric, region & AD infrastructure Your data, users & IAM policies, and configuration of the services you use
🎓
Exam TipTwo responsibilities you'll be asked about — Provider (Oracle): physical security of the data center. Customer (You): configuring IAM policies and encrypting your data. These are the safest example answers.
1.3Governance

Compartments & Tagging Strategy

Compartments are logical folders for resources. Tags are labels on those resources. Together they let you split one tenancy across many teams cleanly.

A compartment is a logical container. Every OCI resource lives in exactly one compartment. IAM policies are almost always written against compartments — that's how you give a team access to only their stuff.

Example compartment hierarchy

📁 root (tenancy)
├─ 📂 Prod
│ ├─ 📂 Prod-Web → VCN, LB, Compute
│ ├─ 📂 Prod-App → Compute, Vault
│ └─ 📂 Prod-DB → Autonomous DB, Backups
├─ 📂 Dev
│ ├─ 📂 Dev-Sandbox → Free-tier resources
│ └─ 📂 Dev-Shared → Shared services
└─ 📂 Security → Audit logs, Vault, Bastion

Tagging: give every resource a label

Tags are key–value labels attached to resources. Two kinds:

Free-form

🏷️ Free-form Tags

Any key, any value. No governance. Good for quick notes; bad for enterprise-scale.

Governed

🔒 Defined Tags

Keys defined in a tag namespace by an admin. Values can be constrained. Use these for cost allocation and policy enforcement.

❓
Why it matters for the examThe tenancy operating-model question in your paper asks for a compartment structure. Answer with: root → environment (Prod/Dev) → application/team compartments, plus a separate Security compartment for audit and vault resources.
1.4IAM

Identity Domains, Users, Groups, Policies & Federation

Who you are (identity), what you can do (policy), and how you sign in without creating a new password for every cloud (federation).

Container

🏛️ Identity Domain

A self-contained identity solution — its own users, groups, applications, and sign-in policies. A tenancy can have several.

Actor

👤 User

A single principal — a person or an application. Users authenticate; they don't get permissions directly.

Collection

👥 Group

A set of users. Permissions are granted to groups, not to users individually.

Rule

📜 Policy

A statement of who can do what. Grammar: Allow group <G> to <verb> <resource> in compartment <C>

Federation & SSO — one login, many clouds

Federation trusts identities from an external identity provider (Microsoft Entra ID, Okta, Active Directory). Users sign in there, and OCI accepts their token. SSO (Single Sign-On) is the user-visible outcome: sign in once, access everything.

🎓
Exam TipNever grant permissions to a user directly. Always create a group, attach the user to the group, and write the policy against the group. This is testable and interviewable.
⚠️
Common TrapPolicies use verb families: inspect (weakest, list only) → read → use → manage (strongest, full CRUD). Don't grant manage when use is enough. Least privilege is exam-tested.

2.2Security Fundamentals

Defense-in-Depth

Never rely on one wall. Stack layers of controls so that if one fails, the next one still holds.

Think of your OCI environment as an onion. An attacker must peel through every layer to reach the data. Each layer is independent.

Click a layer above
Each ring is an independent security layer. If one breaks, the ones beneath still protect the data.
🎓
OCI Example (exam answer)"Attacker gets past the load balancer → NSG blocks the port → Security List blocks the subnet → the OS firewall drops the packet → IAM policy denies the API call → data is encrypted with a customer-managed key." That's defense-in-depth.
2.3Security Fundamentals

Zero Trust vs Traditional Perimeter

The old model: trust the network. The new model: trust nothing, verify everything.

🏰 Traditional Perimeter

Build a strong outer wall (firewall). Inside = trusted. Outside = untrusted. Once you're in the LAN, you can usually reach most things.

Fails when: the attacker gets one credential and moves laterally through the network.

🛑 Zero Trust

No implicit trust anywhere. Every request is authenticated, authorized, and encrypted — even inside the network.

Core principles: Verify explicitly · Least privilege · Assume breach.

🎓
Exam TipOne-line Zero Trust principle: "Never trust, always verify." Every request re-authenticates and re-authorizes regardless of where it comes from.
2.4Security Posture

Three OCI services that watch, block, and guide. They sound similar — but only one prevents risky actions.

ServiceWhat it doesMode
☁️ Cloud Guard Continuously scans your tenancy for risky configurations and suspicious activity. Uses detectors (find problems) and responders (fix them). Detects (and can auto-respond)

2.5Governance

Organization Management

When one tenancy isn't enough, OCI Organizations let you group multiple tenancies for central billing and governance.

Big companies often need separate tenancies — one per business unit, per region, or per environment (Prod isolated from Dev). Organization Management gives you:

  • Centralized billing — one invoice across all child tenancies.
  • Consolidated governance — apply security and cost policies from the parent.
  • Cross-tenancy visibility — usage and cost reports rolled up.
❓
When to use compartments vs tenanciesSame team, different apps → compartments. Different legal entities or hard security boundaries → separate tenancies under one Organization.

3.2Networking

IPv4, CIDR & Subnetting

CIDR notation writes a whole subnet in one number. The prefix length tells you how many addresses it holds.

Formula: a /N block contains 2^(32-N) addresses. So /24 = 2^8 = 256 addresses; /28 = 2^4 = 16; /16 = 2^16 = 65,536.

Try it: CIDR calculator

Enter a CIDR block. See the exam-important numbers immediately.

256Total addresses
3OCI reserved
253Usable hosts
255.255.255.0Subnet mask

In OCI, every subnet reserves 3 addresses: the network address (.0), the broadcast address (last), and one for the subnet's default gateway.

🎓
Exam-question walkthroughFor 10.0.0.0/24: 256 total, 3 reserved (network, broadcast, gateway), 253 usable hosts. Memorize this exact answer — it's a direct question on your paper.
3.3Protocols & Security

TLS/SSL & SSH — Reading the Error Message

The error tells you the layer that failed. Timeout = network. Permission denied = authentication.

Click either error to see what it actually means.

ssh: connect to host 129.146.42.7 port 22: Operation timed out
The connection never even reached SSH.
Permission denied (publickey).
SSH answered — it just rejected you.
Timeout → Network-layer problem
Your packets never got a reply. Check in this order:
  • NSG / Security List — is port 22 allowed inbound from your IP?
  • Route table — does the subnet have a route to an Internet Gateway (for public IPs)?
  • Public IP — was one actually assigned to the instance?
  • OS firewall (iptables/firewalld) — usually open on port 22 by default in OCI images, but check.
🎓
Exam-question walkthroughTimeout ⇒ network path is blocked (NSG/Security List/routing). "Permission denied (publickey)" ⇒ network is fine, key/user is wrong (wrong private key, wrong username like ubuntu vs opc, or missing authorized_keys).
3.4Networking

Load Balancer Basics — Debugging 502

A 502 means the LB got a bad or no response from the backend. But the backend "looks healthy"…

An OCI Load Balancer has three moving parts you need to understand:

Front door

👂 Listener

The port the LB listens on (80, 443). Terminates TLS if configured. Matches to a backend set via rules.

Pool

🎯 Backend Set

The group of instances the LB forwards traffic to. Has a health check policy.

Check

❤️ Health Check

The LB pings each backend on a specific URL/port. Unhealthy backends are removed from rotation.

Why 502 with healthy backends?

CauseWhere to check
Backend listens on a different port than the LB is sending toBackend set → port
Health check reports healthy on port 80, but app actually runs on 8080Backend set → health check URL & port
NSG on the backend blocks the LB's source IPsBackend NSG / Security List
App returns non-2xx (e.g. 500) — LB relays it as 502Backend app logs
TLS/SSL misconfiguration between LB and backendBackend set → SSL config
🎓
Exam TipTwo quick causes: (1) wrong backend port, (2) NSG/Security List blocking the LB → backend traffic. Look in the backend set configuration and the NSG attached to the backend instances.
3.5Tooling

OCI Cloud Shell & OCI CLI

Two ways to run OCI commands: a browser terminal (zero setup) or your laptop (needs config). The auth model is different.

In-browser

☁️ Cloud Shell

Free Linux terminal built into the OCI console. Pre-installed with the CLI, Ansible, Terraform, kubectl. Auth is automatic — it uses your console session token.

Day 4 · 6 topics

Infrastructure as Code

Stop clicking in the console. Write the infrastructure as text, review it in Git, deploy it with one command. Terraform is the tool. OCI Resource Manager is the managed service.

4.1IaC Concepts

Declarative vs Imperative & Idempotence

Two philosophies. One property. All three come up on the exam.

Describe outcome

📝 Declarative

"I want this state to exist." You describe the goal. The tool figures out the steps. Terraform, Kubernetes manifests, CloudFormation.

Describe steps

🔧 Imperative

"Do this, then this, then this." You describe the sequence of actions. Bash scripts, Ansible tasks (partly).

Idempotence — the property that makes IaC safe

A tool is idempotent when applying it repeatedly produces the same end state. Run terraform apply once → resources are created. Run it again with no changes → nothing happens. Run it after editing the file → only the diff is applied.

Contrast with an imperative script that creates a resource: run it twice and you may get two resources or an error.

🎓
Exam TipOne-liner definitions: Declarative = "describe the state you want." Imperative = "describe the steps to get there." Idempotence = "running the same thing twice gives the same result as running it once."

4.3Terraform

Terraform State & State Locking

The state file is Terraform's memory of what it created. Lose it, and Terraform loses track of your infrastructure.

After every apply, Terraform writes a terraform.tfstate file mapping each resource in your code to the real cloud resource it manages. Without this file, Terraform doesn't know that oci_core_instance.web in your code corresponds to a specific instance OCID in the cloud.

Why remote state matters

Team access

👥 Shared source of truth

State on your laptop = only you can apply. State in a shared backend (OCI Object Storage, S3, etc.) = the whole team can collaborate.

Safety

🔒 Locking

A remote backend with locking prevents two people from running apply at the same time. Without a lock, a race condition can corrupt state.

The race condition: two engineers, one local state

👩‍💻 Engineer A (local state)
10:00 — reads state file
10:01 — plans: create web-01
10:02 — apply succeeds ✓
10:03 — writes state locally
👨‍💻 Engineer B (own local state)
10:00 — reads own outdated state
10:01 — plans: create db-01
10:02 — apply succeeds but state is stale
10:03 — overwrites — web-01 lost from state!

Result: cloud has both instances, but Terraform state only knows about one. Next terraform destroy orphans the other.

🎓
Exam TipTwo reasons to keep state remote: (1) team collaboration, (2) locking prevents concurrent-apply corruption. Bonus reason: state files often contain secrets — Object Storage encrypts at rest, your laptop maybe doesn't.
4.4OCI Resource Manager

OCI Resource Manager & Stacks

Terraform-as-a-service, hosted by Oracle. You give it your .tf files, it runs the workflow for you.

A Stack in Resource Manager is essentially your Terraform configuration + its state + a run history, all managed by OCI. You upload the config (from a zip, from Object Storage, from Git), and RM runs plan/apply/destroy on your behalf.

Why use it instead of Terraform on your laptop?

No install

🚀 Zero setup

No Terraform binary, no provider install, no laptop config. Runs entirely in OCI.

Managed state

🗃️ State handled for you

Remote state, locking, and encryption at rest are built in. No S3/Object-Storage backend to configure.

Audit

📋 Everything is logged

Every plan and apply is a Job with a timestamped log. Full audit trail for compliance.

IAM-native

🔐 IAM permissions

Access to a stack is controlled by IAM policies — no separate secret management.

🎓
Exam-question walkthroughTwo RM advantages over laptop Terraform (any two): (1) managed remote state with locking, (2) IAM-integrated access control, (3) audit-logged job history, (4) no local install required.
4.5OCI Resource Manager

Drift Detection

Someone edited a resource in the console. Now the real cloud doesn't match your Terraform code. That's drift.

Drift is any difference between the state Terraform expects and the state that actually exists in the cloud. It happens when someone bypasses IaC — edits a security list in the console, deletes an instance manually, changes a tag.

How Resource Manager finds it

Resource Manager has a built-in Drift Detection action on every stack. Click "Detect Drift" and RM:

  1. Reads the current cloud state via APIs.
  2. Compares it to the stack's Terraform state.
  3. Reports each resource as In Sync, Modified, or Deleted.
# Drift Detection Report
✓  IN SYNC    oci_core_vcn.main
~  MODIFIED   oci_core_security_list.web
             expected: ingress port 80 only
             actual:   ingress ports 80, 22
✗  DELETED    oci_core_instance.web_02
             (removed outside Terraform)
🎓
Exam TipThe one-line answer: Drift = "cloud state has diverged from Terraform state." The OCI feature that reports it = Resource Manager's Drift Detection.
4.6OCI Resource Manager

Resource Discovery

You inherited a compartment full of hand-built resources. Resource Discovery generates Terraform code for what's already there.

Resource Discovery is a Resource Manager feature that scans an existing compartment and produces:

  • A set of .tf configuration files describing every resource it finds.
  • A Terraform state file mapping those files to the real resources.

The result: you can adopt an already-running environment into Terraform without rebuilding it.

🎓
Exam-question walkthrough"Which RM capability generates Terraform configuration + state from resources that already exist in a compartment?" → Resource Discovery.
Day 5 · 6 topics

VCN, Compute & Storage

Where your applications actually run. Design the network, launch the compute, choose the right storage — and understand why a private DB subnet never touches the internet.

5.1VCN Architecture

VCN — Three-Tier Design

The exam-standard architecture: public web tier, private app tier, private DB tier. Each subnet has its own routing rules.

A VCN (Virtual Cloud Network) is your private network in OCI — a big CIDR block (e.g. 10.0.0.0/16) sliced into subnets. Subnets are labelled public or private based on whether they get public IPs and how they route to the internet.

Blueprint: three-tier web application

VCN 10.0.0.0/16
🌐 Web Tier — PUBLIC subnet 10.0.1.0/24
Route → Internet Gateway (0.0.0.0/0)
Contains: the Load Balancer (public IP). Accepts internet traffic on 80/443.
⚙️ App Tier — PRIVATE subnet 10.0.2.0/24
Route → NAT Gateway (for outbound patching/updates only)
Contains: application compute instances. Only reachable from the LB. Can call out to the internet for updates, but internet cannot call in.
🗄️ Database Tier — PRIVATE subnet 10.0.3.0/24
Route → Service Gateway (Oracle Services only)
Contains: the Database (Autonomous DB or DB System). Only reachable from the app tier. No internet access — uses Service Gateway for backups to Object Storage.
🎓
Exam-question walkthroughThree-tier design answer: Web tier — public subnet, IGW, holds Load Balancer. App tier — private subnet, NAT GW for outbound. DB tier — private subnet, SGW for Oracle-service traffic, holds the database.

Internet Gateway (IGW)
Two-way traffic between a public subnet and the internet. Use it for public-facing resources (web servers, load balancers) that need to be reachable from the internet.
⚠️

The DB needs to send backups to Object Storage (an Oracle service) — SGW keeps that traffic on Oracle's private backbone, never touching the public internet. It's more secure and it's free.
5.3VCN Security

Two ways to write virtual firewall rules in OCI. Both work at the packet level. The difference is what you attach them to.

Exam TipThey stack. If both a Security List and an NSG apply to a VNIC, traffic must be allowed by either one (rules are OR'd together, not AND'd). Also: NSGs let you reference other NSGs as a source — that's how "allow LB → app" is written cleanly.
5.4Compute Automation

Compute Instances & cloud-init

cloud-init is the tiny piece of software that runs on first boot and applies your customizations. Pass it a script or a YAML file as "user data."

When you launch a compute instance in OCI, you can attach user data — a text blob cloud-init interprets on the very first boot. This is how you install packages, start services, and drop configuration files without ever SSH-ing in.

cloud-config to install and enable a web server

#cloud-config

package_update: true

packages:
  - httpd

runcmd:
  - systemctl enable httpd
  - systemctl start httpd
  - firewall-cmd --permanent --add-service=http
  - firewall-cmd --reload
  - echo "<h1>Hello from OCI</h1>" > /var/www/html/index.html

Paste this into the Advanced options → User data field when launching an Oracle Linux instance. On first boot: package installed, service enabled, firewall opened, homepage created.

🎓
Exam TipThe header #cloud-config is required — it's how cloud-init knows to parse the file as YAML instead of a shell script. Without it, cloud-init tries to execute the YAML as bash and fails.
5.5Block Storage

Boot Volume vs Block Volume

Two flavors of block storage in OCI. One boots the OS, the other adds data disks. Only one supports multi-attach.

OS disk

💿 Boot Volume

Automatically created when you launch a compute instance. Contains the OS. Attached to exactly one instance.

Data disk

💾 Block Volume

Extra data disks you attach to instances after launch. Sizes 50 GB → 32 TB. Supports multi-attach.

Multi-attach — one volume, many instances

A block volume can be attached to up to 8 instances simultaneously for shared-storage scenarios (clustered databases, shared file processing).

The filesystem catch: a normal filesystem (ext4, xfs) will corrupt if two instances write to it at the same time. Multi-attach only works safely with a cluster-aware filesystem (OCFS2, GFS2) or a database that has its own coordination (Oracle RAC).

⚠️
Exam-critical trap"Which supports multi-attach?" → Block volume (not boot). "What filesystem requirement?" → a cluster-aware filesystem like OCFS2 — never a plain ext4/xfs, or the shared writes will corrupt the data.
5.6Compute Access

SSH Key Injection

How your public key ends up on a fresh Linux instance's ~/.ssh/authorized_keys, without you ever setting a password.

When you launch an OCI compute instance, you paste a public SSH key. Behind the scenes:

  1. The public key is passed to the instance as instance metadata.
  2. On first boot, cloud-init reads that metadata and writes the key into /home/opc/.ssh/authorized_keys (on Oracle Linux; /home/ubuntu/ on Ubuntu).
  3. You SSH in with the matching private key — no password ever set.

Day 6 · 3 topics

Encryption & Key Management

Where cryptographic keys live in OCI, how one key protects another, and why HSM-protected keys cost more.

6.1Key Management

OCI Vault & KMS

Vault is the OCI service that stores and manages your cryptographic keys and secrets. KMS is the API layer that uses them.

Vault is a container. Inside it, you create:

Keys

🔑 Master Encryption Keys (MEKs)

The top-level keys. Used to encrypt other keys (envelope encryption). Never leave the Vault.

Secrets

🤫 Secrets

Arbitrary text values — DB passwords, API tokens, TLS certificates. Versioned. Retrieved by ID.

Ops

🔄 Key Rotation & Replication

Rotate a key on schedule (invalidates old versions gracefully). Replicate a vault to another region for DR.

🎓
Exam TipVault + KMS work together with IAM. Only groups with a policy like Allow group AppUsers to use keys in compartment X can call KMS to encrypt/decrypt. This is how "encryption at rest with customer-managed keys" is actually implemented.

6.3Key Protection

Key Protection Modes — Software vs HSM

Two ways OCI can store your MEK. Both are secure. HSM is stronger, more expensive, and required for some compliance regimes.

Cheaper

💻 Software-protected

The MEK is stored encrypted on disk. Cryptographic operations happen in software on regular servers. Good for most workloads.

Stronger

🔒 HSM-protected

The MEK lives inside a Hardware Security Module — a dedicated, tamper-resistant chip (FIPS 140-2 Level 3 certified). The key never leaves the HSM in plaintext, ever.
